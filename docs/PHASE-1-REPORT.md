# Phase 1 — Migrations and startup

**Goal:** make the database reliably upgradable, so every later phase can change
a model without fear.

---

## 1. The reported defect was not the defect

The brief lists as finding #3:

> Alembic tree has 3 heads, 2 roots and a fork — `alembic upgrade head` fails
> outright. Heads: `b3d7e91c2a45`, `307efdf1db45`, `c1a7f4e9b8d2` · Roots:
> `4823c6c0b288`, `2668e3beafa9`

Asked directly, alembic disagreed:

```
$ docker exec ghawy_backend alembic heads
c9e1d3a7b542 (head)
$ docker exec ghawy_backend alembic current
c9e1d3a7b542 (head)
```

One root, one head, no missing parents, production stamped at head. Parsing the
48 files independently agrees.

The three "extra heads" are the two parents of
`4823c6c0b288_merge_multiple_heads.py` plus the pre-`c9e1d3a7b542` head; the
"second root" is that merge itself. Its `down_revision` is a **tuple spanning two
lines**, so a line-oriented parser sees a revision with no parent (a root) and
two revisions nobody points at (heads). The fork at `f1201efadb0f`
(`9b2d6f5a8c31` / `e478012af2b4`) is real, and that merge has always closed it.

No merge revision was needed. Nothing was deleted, and no `down_revision` was
edited to silence an error.

## 2. The defect that was real

`alembic upgrade head` against an **empty** database did fail — for a different
reason, four revisions in:

```
sqlalchemy.exc.ProgrammingError: (psycopg2.errors.UndefinedTable)
relation "comment_reactions" does not exist
[SQL: ALTER TABLE comment_reactions ADD UNIQUE (comment_id, user_id)]
```

Measured across the 48 revisions:

| | count |
|---|---:|
| Tables declared by `models.py` | 50 |
| Tables any migration creates (`op.create_table` / raw `CREATE TABLE`) | **8** |
| Revisions whose `upgrade()` is empty (`pass`) | 6 |

The eight are `audit_records`, `chat_message_reactions`, `coupon_redemptions`,
`coupons`, `exam_attempts`, `exams`, `legacy_emails`, `project_submissions`.
The other 42 tables existed only because `Base.metadata.create_all()` ran at
import. `--autogenerate` was then run against a database `create_all` had
already updated, so it correctly found nothing to do — which is how five
revisions titled "add *X* table" contain no code at all. Six revisions have an
empty `upgrade()` in total: those five, plus the merge `4823c6c0b288`, which is
empty because that is what a merge revision is (F-13).

So the history replayed only against a database that already had the schema.
That is the rot, and it is what made every model change a gamble.

## 3. Model ⇄ production drift, found and closed

Before writing a baseline I checked the models actually describe production, by
diffing `pg_dump --schema-only` of the live database against a `create_all` of
the models. Seven substantive differences — all cases where a migration did the
work and `models.py` was updated by hand without it:

| Column | Production | `models.py` said |
|---|---|---|
| `users.is_owner` | `NOT NULL` | nullable |
| `courses.sort_order` | `NOT NULL`, indexed | nullable, no index |
| `lessons.is_project` | `NOT NULL` | nullable |
| `coupons.is_active` | `DEFAULT true` | no server default |
| `coupon_redemptions.status` | `DEFAULT 'pending'` | no server default |
| `coupon_redemptions.currency` | `DEFAULT 'EGP'` | no server default |
| `admin_member_notes.note` | `DEFAULT ''` | no server default |

Plus `admin_member_notes.id` carried a redundant `index=True` production does not
have (it is the primary key). All corrected in `models.py`, in production's
direction — production is authoritative. These are DDL-level attributes; no
query, no ORM behaviour and no API response changes.

Three remaining differences are naming-only and were deliberately left alone
(F-12).

## 4. The fix

**`ghawy_baseline`** — `alembic/versions/0000_ghawy_baseline_schema_snapshot.py`,
the new root of the history. Creates all 50 tables with every index, constraint,
default and foreign key. Generated by `--autogenerate` against an empty database
*after* the model corrections above, then verified against production byte by
byte (§5). It is a frozen snapshot, not something regenerated from the models.

The old root `2668e3beafa9` now has `down_revision = 'ghawy_baseline'`. That is
the only `down_revision` edited, and it attaches a new parent rather than hiding
a broken one.

**`backend/migration_utils.py`** — one helper, `baseline_created_schema()`,
true exactly when the `ghawy_schema_baseline` marker table exists.

**The 42 pre-baseline revisions that do real work** each gained four lines, in
`upgrade()` and `downgrade()`:

```python
# Predates ghawy_baseline: on a database built from that snapshot this
# change is already present, so there is nothing to apply.
if baseline_created_schema():
    return
```

The marker is written **only** by the baseline, and only when the baseline
genuinely created the schema — if it finds a `users` table already there it
returns immediately and writes nothing, so a legacy unstamped database still
gets the full historical treatment. This is what makes the guard exact rather
than a blanket "skip old migrations":

| Database | `ghawy_baseline` does | The 42 historical revisions do |
|---|---|---|
| Empty | creates 50 tables, writes marker | skip |
| Production, or a dump of it | never runs (already an ancestor) | run for real if pending |
| Has tables, never stamped | nothing, **no marker** | run for real |

Skipping the historical revisions on a fresh database also stops five data
migrations from replaying — including `a7f1c93d20b4`, which embeds **491 real
member email addresses**. A developer's laptop database has no business
containing those.

## 5. Verification

All against an isolated scratch Postgres (`ghawy_scratch_pg`) and a throwaway
container, printed before every run:

```
DATABASE_URL=postgresql://scratch:scratch@ghawy_scratch_pg:5432/ghawy_scratch
```

The production container was never used to run migrations, and the one file
copied into it during investigation was restored from its own image
(sha `4f90fc8e2bc8b37e`, verified equal). Production was not restarted, not
rebuilt and not deployed to. It has been `Up … (healthy)` throughout.

**① Clean database → head.** Exit 0, all 49 revisions, ends at `c9e1d3a7b542`.

**② The resulting schema equals production's.** `pg_dump --schema-only` of both,
normalised and sorted, diffed. **Zero substantive differences** — every column,
type, nullability, default, index and foreign key matches. What remains is the
three naming-only items in F-12, plus `alembic_version`, the new
`ghawy_schema_baseline`, and production's orphan `subscription_repair_2026_08_14`
(F-03).

**③ A production database with data upgrades with no loss.** Full 34 MB
`pg_dump` of production restored to a scratch database, `alembic upgrade head`
run against it. Clean no-op. Row counts for all **52 tables identical** before
and after — `users` 1912, `messages` 12043, `message_reads` 86274, `payments`
1487, `notifications` 5890, `user_progress` 5502, `email_campaign_sends` 3385,
`certificates` 565, and so on.

**④ The guard does not fire on a legacy database.** On that clone: dropped
`users.inactive6_email_sent_at`, rewound the stamp one revision, ran
`alembic upgrade e4f5a6b7c8d9`. The revision **really ran** and the column came
back; 1912 users untouched.

> An earlier attempt at this test rewound the stamp *nine* revisions while
> undoing only one column, so a later revision hit `column "first_name" already
> exists` and Postgres's transactional DDL rolled the whole run back. That was
> the test being wrong, not the code — recorded here because the first output
> looked like a failure.

**⑤ A database with tables but no stamp.** Dropped `alembic_version` from the
clone, ran `alembic upgrade ghawy_baseline`. Baseline no-opped, wrote no marker,
1912 users untouched — so the history below it remains live for that database.

**⑥ The app boots.** `GET /` → 200. Threadpool raised to 120, all six scheduler
jobs registered (`daily_subscription_check_job`, `check_expiring_subscriptions`,
`check_5day_expiry`, `check_birthdays`, `check_inactive_6day`,
`send_winback_emails`), clean shutdown with the scheduler stopped.

**⑦ Booting against a schema-less database refuses, and says why.**

```
RuntimeError: The database has no schema. Run `alembic upgrade head` before
starting the app (or set DEV_CREATE_ALL=1 outside production to build it from
the models).
```

**⑧ Seeding happens once, not once per worker.** Three concurrent processes
called `_seed_once()` against a freshly migrated database. All exited 0;
`categories=4 channels=4 coupons=2 guests=5 courses=4` — one set of rows, no
duplicates, no unique-constraint casualties.

## 6. Startup path

`Base.metadata.create_all()` and `seed_defaults()` ran at **import** time
(`main.py:285-286`) — once per Gunicorn worker, before the app object existed.
Both now run inside a `lifespan` handler.

The three existing `@app.on_event` handlers moved into it as well, and this was
not optional: FastAPI **silently ignores** `on_event` handlers when a `lifespan`
is passed. Leaving them would have killed the anyio threadpool bump (the fix for
the 2026-07-21 26-minute outage) and APScheduler, with no error anywhere.
Verified running in ⑥.

`create_all` is off the production path. Missing schema is now a loud refusal;
`DEV_CREATE_ALL=1` outside production restores the old shortcut for local work,
and is no longer needed anyway — `alembic upgrade head` works from empty.

## 7. Reversibility

`ghawy_baseline.downgrade()` drops the marker and all 50 tables — correct for the
revision, and total data loss if anyone runs it against a real database. It
exists for symmetry; it is not a maintenance operation.

The 42 guarded `downgrade()`s carry the same guard as their `upgrade()`: on a
baseline-built database they are no-ops, because the change they would undo was
never separately applied. Downgrading below `ghawy_baseline` on such a database
means going to `base`, i.e. dropping everything.

Nothing else changed reversibility. No migration file was deleted.

## 8. Not deployed

The backend is baked into its image, so none of this is live. Deploying means
`docker compose -f docker-compose.prod.yml up -d --build backend`, which runs
`alembic upgrade head` first — a verified no-op against production (③) — and
then restarts the worker.

That restart is not free: it drops every WebSocket connection and can saturate
the DB pool on reconnect. **Awaiting your go-ahead.**
