## Part A — the four Phase 1 follow-ups

### A1. The two unlisted verifications, and the one that was genuinely missing

The Phase 1 report listed eight verifications (①–⑧); the summary message named
three and said "five directions", which was sloppy. The five were ①–⑤: the three
named, plus **② the clean-migrated schema equalling production's** and **⑤ a
database with tables but no stamp**.

**Your instinct was right about ⑤.** It only ran `alembic upgrade ghawy_baseline`
— a single step — and confirmed the baseline no-opped and wrote no marker. It
never showed the historical revisions *replaying*. The guard's central claim was
unproven. Now proven, three ways:

**⑨ A 33-revision replay on a marker-less database with real data.** Took a fresh
production clone (1912 users, 12,044 messages), downgraded it 33 revisions to
`aaa10e9ec801` — a genuinely older schema: no `users.token_version`,
`staff_permissions`, `team_role`, `first_name`, `legacy_promo_round`,
`password_reset_code` or `inactive6_email_sent_at`; no `coupons`, `exams` or
`admin_member_notes` tables — then ran `alembic upgrade head`.

All **33 revisions genuinely applied** (exit 0). Every column and table came
back, the marker table never appeared, and `pg_dump --schema-only` of the result
against production diffs to **0 lines**. Row counts unchanged: users 1912,
messages 12,044, payments 1487.

**⑩ Why it could not go deeper.** `aaa10e9ec801`'s `downgrade()` is broken —
pre-existing, logged as F-15. It converts `project_submissions.status` back to a
Postgres enum `projectsubmissionstatus` that nothing recreates and that never
existed in production, because `create_all` made that column a String from the
start. So the chain downgrades 33 revisions and no further. Phase 1's guard is
not involved: it returns early only when the marker exists, and there is no
marker on that database — the original code ran, unchanged, and failed.

**⑪ The `alembic_version`-absent case, answered honestly.** Dropped
`alembic_version` from a clone whose schema is current, ran `upgrade head`:

```
Running upgrade  -> ghawy_baseline          ← no-op, users table already there
Running upgrade ghawy_baseline -> 2668e3beafa9
psycopg2.errors.DuplicateColumn: column "video_status" of relation "lessons" already exists
```

The baseline no-opped, wrote **no marker**, and the next revision ran **for
real** — it tried to add a column that already existed. No short-circuit. But
the run fails, and that is correct rather than a regression: alembic cannot infer
where an unstamped database sits in its history, and it could not before Phase 1
either. The supported recovery is `alembic stamp <matching revision>`; verified
that after `alembic stamp head`, `upgrade head` is a clean no-op with all 1912
users intact. Logged as F-16.

### B3. Seed logic review

* **Writes on every startup?** No. Every block is guarded by a count or an
  existence check; a second run issues only SELECTs.
* **Can it overwrite real data?** No. Existing rows are never modified. The
  coupon block explicitly leaves a tuned `discount_percent` or `max_redemptions`
  alone.
* **Duplicate seeding?** The coupons are seeded both here and by migration
  `b6c7d8e9f0a1`. Deliberate and documented, and now load-bearing — see B2.
* **Does it slow deployment?** No. On an already-seeded database it is a handful
  of counts.
* **Ordering vs `alembic upgrade`.** The container command is
  `sh -c "alembic upgrade head && gunicorn …"`, so migrations finish before the
  app process starts and the `lifespan` seed therefore always runs against a
  migrated schema. `_bootstrap_schema()` runs first inside `lifespan` and refuses
  to start if the schema is missing.
* **Once per boot, not per worker?** Yes — advisory lock, re-verified in ⑯.

### B5. Production reality — the cleanup script (staged, NOT executed)

The rows are in the production database and are served unauthenticated.
**Production still has all 5 guests and 5 guest_sessions — verified after every
test.** Nothing was executed against it.

**Checked first, as you asked: has anything touched those rows?** No.

* All 5 `guests` rows match the seed literals **exactly** — title, company,
  `sessions_count`, `attendees_count`, `rating`. No admin has edited one.
* None has an `avatar_url`, so nobody uploaded a picture for one.
* All 5 `guest_sessions` have empty `platform` and `session_url`,
  `attendees_count = 0` and `rating = 0.0` — nobody scheduled or ran one.
* All ten rows were created in the **same second** (`2026-07-09 19:47:20`) —
  one seed run.
* Nothing links to them: `guest_sessions.guest_id` is the only foreign key to
  `guests` in the whole schema, and `session_bookings`, `session_reminders`,
  `session_projects` and `live_attendees` are all empty in production.

**`backend/scripts/cleanup_seeded_public_figures.py`** — 160 lines, dry-run by
default.

*Exactly what it would remove:* **5 rows from `guests`** (ids 33, 34, 35, 36, 37)
and **5 rows from `guest_sessions`** (ids 33–37). Nothing else, in any table.

*Safety:* it re-checks the fingerprint of every row at run time and **aborts
without deleting anything** if any row differs from what the seed wrote, or has
an avatar, or has a session with a real platform/URL/attendees/rating. It writes
a timestamped JSON backup of all ten rows first — and proves the backup path is
writable **before** the DELETE, not after.

*Tested on clones, never on production:*

* Dry run on a faithful production clone: listed all ten rows, "All rows match
  the seeded fingerprint exactly", deleted nothing.
* The abort path fired for real on my replay clone (its counts had been reset by
  the 33-revision downgrade cycle) and refused to delete — good.
* A first `--apply` attempt **failed on the backup write** (`/app` is not
  writable, the image runs as non-root `appuser`) and, because writability is
  proved first, **nothing was deleted**. That is why the script now takes
  `--backup-dir` and pre-checks it.
* `--apply` on the clone: `deleted: 5 guests, 5 guest_sessions`, verification
  `rows with those five names remaining: 0`, backup file holds all ten rows.
  Collateral check: users 1912, messages 12,044, payments 1487,
  suggested_guests 1 — all unchanged.
* Booted the Phase 2 backend against that cleaned clone: **guests stayed 0**.
  The rows do not come back.

**Order matters, and this is the part to get right (F-18).** The old guard was
`if db.query(Guest).count() == 0`, so deleting these rows against the *old* code
puts them back on the next restart — production's `guests_id_seq` is at 37 for
5 rows, which is that loop's fingerprint. So: **deploy Phase 2 first, then run
the script.**

*How to verify afterwards:*
